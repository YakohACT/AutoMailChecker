# テスト設計

テストは単体・結合・判定精度の評価・性能の4段で行う。受け入れの基準は、重要メールの見逃し率10%以下、誤振り分け率10%以下、3時間で100件以上の処理量の3つである（仕様書13章）。

## 単体テスト

xUnitで書き、IMAP・llama-server・Windowsはインターフェースの偽物に差し替える。

| 対象 | 主な確認点 |
| --- | --- |
| ActionPolicy | 確信度「低」なら移動しない / 広告（無視・振り分け）/ 1件該当 / 複数該当で最優先を選ぶ / 最優先に振り分け先がなければ次点 / 無効な項目を無視 / allowMoveがfalse |
| SenderFilter | 完全一致、ドメイン一致、大文字小文字、表示名付きのアドレス |
| BodyPreprocessor | HTMLのみのメール、引用と署名の除去、転送本文が残ること、URLの短縮、4,000字超の切り詰め |
| PromptBuilder / SchemaBuilder | 有効な項目だけがenumに入る、有効な項目が0件のとき、設定が同じなら指示文が1文字も変わらないこと |
| LlamaClassifierの応答検証 | 壊れたJSON、知らない項目ID、重複、長すぎる要約、途中で切れた応答、時間切れ |
| PauseController | 条件が重なったときの優先順（完全停止 ＞ 判定保留 ＞ 低負荷）、解除後60秒の待ち |
| ProcessRuleMatcher | 実行ファイル名、タイトルの部分一致、両方指定、Steam・Epic・DMMのパス判定、ランチャー本体を除くこと |
| ConfigService | 保存時の検証、変更の検知と反映、.bakへの退避 |
| SqliteStateStore | スキーマの移行、保持期間での削除とkeepの扱い、判定1件分のトランザクション |

## 結合テスト

テスト用のIMAPサーバー（Dovecotなど）を手元に立てるか、テスト専用のメールアカウントを使う。llama-serverは本物と、決まった応答を返す小さな偽サーバーの両方で確かめる。

| ID | シナリオ | 期待する結果 |
| --- | --- | --- |
| IT-01 | 新着1通（項目1件に該当） | 項目のフォルダーへ移動し、未読のまま。履歴はoutcomeがmoved |
| IT-02 | 項目2件に該当 | 優先度の高い方へ移動。履歴に両方の項目が残る |
| IT-03 | 除外リストの送信者 | 本文を取得せず、判定履歴なし。processed\_messageにexcludedで残る |
| IT-04 | 広告（無視 / 振り分け） | 受信トレイに残る / 広告用フォルダーへ移動 |
| IT-05 | 確信度「低」 | 受信トレイに残り、outcomeがkept\_low\_confidence |
| IT-06 | 振り分け先がサーバーにない | 移動せず、トレイアイコンが警告表示。outcomeがkept\_no\_folder |
| IT-07 | 別アカウントのフォルダーを振り分け先に設定 | 保存時に検証エラー。どの経路でもアカウントをまたぐ移動が起きない |
| IT-08 | 切断中に新着 | 再接続後のUID検索で回収される |
| IT-09 | UIDVALIDITYが変わる | 再走査し、同じメールを二重に処理しない |
| IT-10 | 完全停止中に5通届く | 停止中はllama-serverのプロセスがなく、再開後に古い順で5通処理される |
| IT-11 | 低負荷で継続に切り替わる | GPUを使わない設定で起動し直し、判定が続く |
| IT-12 | 元に戻す（COPYUIDあり / なし / すでに別の場所） | 受信トレイに戻る / Message-IDで探して戻る / 何もせずその旨を表示 |
| IT-13 | お試し仕分け（結果の表示のみ） | 移動は0件、全件がplanned。起点UIDは変わらない |
| IT-14 | お試し仕分け（実際に移動）とまとめて戻す | 移動した全件が受信トレイに戻る |
| IT-15 | MOVE非対応のサーバー | COPYと削除で移動。UIDPLUSもなければ移動しない |
| IT-16 | llama-serverが起動しない | 3回起動し直した後、判定保留になりトレイに警告 |
| IT-17 | 移動直後にアプリを強制終了 | 再起動後に二重に移動せず、履歴が補われる |

## 判定精度の評価

評価はアプリの「お試し仕分け」と「誤判定として記録」だけで行えるようにする。専用のツールは作らない。

1. 評価セットを選ぶ: 4アカウントの過去メールから100通以上。各項目10通以上、広告20通以上、どれにも当てはまらないもの20通以上、複数の項目に当てはまるものを含める
2. お試し仕分け（結果の表示のみ）で判定する
3. 判定履歴で全件を見て、間違いに「誤判定として記録」で正解を付ける。記録のないものは正解とみなす
4. 次の指標を出す（お試し仕分けダイアログの「この回の精度」に表示される）

| 指標 | 定義 | 合格線 |
| --- | --- | --- |
| 重要の見逃し率 | 正解が「重要」のうち、重要フォルダーへの移動予定にならなかった割合 | 10%以下 |
| 誤振り分け率 | 移動予定になったもののうち、移動先が正解と違う割合 | 10%以下 |
| 広告の取り違え | 広告でないメールを広告と判定した件数 | 参考値（合否には使わない） |
| 確信度ごとの正解率 | 高・中・低それぞれの正解の割合 | しきい値を決めるのに使う |
| 平均判定時間 | 1通あたりの平均 | 108秒以内 |

- モデルの選定: 同じ評価セットでQwen3.5-9B（GPUとCPUのみ）、Qwen3.5-4B、Qwen3.6-35B-A3Bを比べ、合格したもののうち使うメモリが最も少ないものを既定にする
- 確信度のしきい値: 「中」の正解率が誤振り分け率の合格線を満たさなければ、既定を「高のみ」にする
- 指示文の版を上げたときも、同じ評価セットで前の版と比べる

## 性能テスト

| 項目 | 方法 | 合格線 |
| --- | --- | --- |
| 処理量 | 評価セット100通を途切れなく処理する | 3時間以内 |
| アプリ本体のメモリ | 24時間動かし続け、使用メモリを記録する | 100MB以下で、増え続けない |
| 検知のCPU負荷 | 停止対象の検知だけを1時間動かす | 平均0.1%未満 |
| 停止時のメモリ解放 | ゲームを起動し、llama-serverのプロセスが消えるまでの時間を測る | 処理中の1件の完了から10秒以内 |
| 低負荷で継続 | VS Codeを開いたまま10通を処理する | 判定が止まらない。所要時間は記録だけ |
